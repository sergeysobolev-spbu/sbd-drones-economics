# Быстрый старт: UAS Dev Company

Краткая инструкция для пользователя интерфейса, тестировщика и разработчика прототипа в каталоге `systems/uas_dev_company`. Подробная архитектура, ЦБ и API — в [`README.md`](README.md); общий обзор брокера/SDK репозитория — в [корневом `docs/quick_start.md`](../../../docs/quick_start.md).

Дальше все команды выполняются из **`systems/uas_dev_company`**, если не указано иное.

---

## 1. Развертывание на новой машине

### 1.1. Что должно быть установлено

| Компонент | Зачем |
|-----------|--------|
| **Docker** + **Compose v2** | Сборка и запуск стека (`make docker-up`) |
| **Python 3.12+** | Локальные скрипты и pytest |
| **Pipenv** | Зависимости из `config/Pipfile` (корень репозитория) |
| **Git** | Клон монорепозитория |

Опционально:

| Компонент | Зачем |
|-----------|--------|
| **Node.js 20.19+** (рекомендация экосистемы фронта) | `make e2e-test` (Playwright) |
| Альтернатива диаграммам через Docker | Образ PlantUML уже тянется `make diagrams` |

### 1.2. Клонирование и переход в систему

```bash
git clone <url-репозитория>
cd systems/uas_dev_company
```

### 1.3. Зависимости Python

Из каталога `systems/uas_dev_company` Makefile вызывает `pipenv` с `PIPENV_PIPFILE=../../config/Pipfile`. Установка (один раз на машину/venv):

```bash
cd ../../   # корень монорепозитория
pipenv install --dev
```

Дальше снова `cd systems/uas_dev_company`.

### 1.4. Генерация compose и переменных

Собираются `.generated/docker-compose.yml` и `.generated/.env` из описания системы и подключённых компонентов:

```bash
make prepare
```

**Ожидаемый результат:** в каталоге появились файлы `.generated/docker-compose.yml` и `.generated/.env`; в консоли краткая подсказка по профилям.

### 1.5. Инициализация виртуальных каталогов данных доменов

```bash
make init-data
```

**Ожидаемый результат:** под `resources/domains/` (или путь из `UAS_DOMAIN_DATA_ROOT` после запуска) созданы каталоги доменов; сами базы SQLite появятся при первом обращении воркеров.

### 1.6. Запуск стека

Целевой учебный режим — профиль **`kafka`** (по умолчанию переменная `BROKER_TYPE` в генерируемом `.env`):

```bash
make docker-up
```

**Ожидаемый результат:** образы собраны, контейнеры запущены, брокер в состоянии healthy, шлюз и воркеры подняты. Порт входа пользователя задаётся в `.generated/.env`, обычно **`HTTP_PORT=8080`** (см. раздел FAQ).

Запуск может занять несколько минут при первой сборке.

## 2. Настройка окружения

| Переменная / файл | Назначение |
|-------------------|------------|
| `.generated/.env` | Порты, учётные данные брокера (`ADMIN_USER` / `ADMIN_PASSWORD` → клиент Kafka в compose), `HTTP_PORT`, `JWT_SECRET`, и др. правьте точечно, затем при необходимости `make docker-down && make docker-up`. |
| `BROKER_TYPE` | Выбор транспорта (`kafka`, при необходимости `mqtt` — см. генерацию prepare). |
| `UAS_DOMAIN_DATA_ROOT` | Корень томов доменов внутри контейнеров (по умолчанию путь вида `/app/systems/uas_dev_company/resources/domains`). |
| Корневой `config/` | `Pipfile`, `pyproject.toml` для pytest — не удаляйте при работе только из подкаталога системы. |

Для смежной интеграции по шине и журналам см. переменные в [`README.md`](README.md) (DroneAnalytics, `UAS_ADJACENT_BUS_INTEGRATION`, и т.д.) — это не нужно для первого знакомства с UI на локальном стенде.

## 3. Проверка работоспособности (тесты)

Команды **из `systems/uas_dev_company`**:

| Цель `make` | Что проверяет |
|-------------|----------------|
| `make tests` | Unit + интеграционные pytest **без** поднятого полного compose (часть сценариев пропускается при отсутствии окружения). |
| `make tcb-test` | Те же области + покрытие ≥70%, пересборка `docs/tcb_metrics.json` и `docs/tcb_summary_report.md`. |
| `make test-all-docker` | Поднимает compose, ждёт брокер, прогоняет интеграционные тесты против живого HTTP (должен быть установлен Pipenv как выше). |
| `make e2e-test` | Playwright против **уже работающего** стека; нужен Node и зависимости в `web/`. |
| `make tests-complete` | Полная цепочка (включая docker, часть смежных сценариев, метрики) — долго, для CI или полной регрессии. |

Типичный порядок для разработчика после правок коду:

```bash
make tests
make tcb-test
```

Для регрессии уровня «как CI» после установки Docker/Node при необходимости:

```bash
make tests-complete
```

## 4. Веб-интерфейс: пошагово и ожидаемый результат

Стек должен быть запущен (`make docker-up`). В браузере откройте **`http://127.0.0.1:${HTTP_PORT}`** (чаще всего порт **8080** — смотрите `.generated/.env`).

### Шаг 1. Первый администратор

При **пустой** базе пользователей воркера `user_management` выполните **один раз** создание первого админа через API:

```bash
BASE="http://127.0.0.1:8080"   # подставьте свой HTTP_PORT
curl -sS -X POST "$BASE/api/bootstrap-admin" \
  -H "Content-Type: application/json" \
  -d '{"username":"admin-demo","password":"your-secure-password"}'
```

**Ожидаемый результат:** JSON с данными созданного пользователя или сообщение об ошибке, если администратор уже существует (тогда вход только через `POST /api/login` с известными учётными данными).

Подробнее и переменные Playwright см. раздел авторизации в [`README.md`](README.md).

### Шаг 2. Вход в UI

На странице входа укажите логин и пароль созданного администратора.

**Ожидаемый результат:** переход в защищённую область приложения без сообщения об ошибке аутентификации.

### Шаг 3. Роли и сценарий «разработчик → эксплуатант»

Создайте через UI или API пользователей с ролями «разработчик» и «эксплуатант» (см. таблицы ролей в [`README.md`](README.md)). Далее минимально: подача данных о прошивке, сертификация (учебная заглушка Регулятора), регистр дрона, витрина и покупка.

**Ожидаемый результат:** операции выполняются согласованно (цепочки отражены в UI); при ошибках валидации — понятное сообщение; данные сохраняются в SQLite соответствующих доменов.

### Шаг 4. E2E после ручной проверки

Если UI уже проверен и compose стабильно работает:

```bash
make e2e-test
```

При необходимости задайте `E2E_BASE_URL`, `E2E_ADMIN_USER`, `E2E_ADMIN_PASSWORD` (значения по умолчанию для учётной записи, которую делает фикстура тестов, см. в [`README.md`](README.md)).

**Ожидаемый результат:** все спеки Playwright проходят; при падении см. трассировки в каталоге, который укажет playwright.

## 5. FAQ

### Где искать ошибки Docker / образов?

Логи: **`make docker-logs`** или прямой вывод `docker compose … logs`. Типичная причина — не выполнен `make prepare` перед `docker-up` или конфликт портов.

### Почему после «удаления» данных UI показывает старых пользователей?

Compose по умолчанию использует **именованные тома**. Команда `make docker-down` **не удаляет** тома. Чтобы очистить данные доменов: остановите стек с удалением томов (например, `docker compose … down -v` с тем же файлом compose и профилем, что при запуске), затем снова `make init-data` и `make docker-up`.

### Путаница: `ADMIN_USER` и пароль входа в веб?

В `.env`: **`ADMIN_USER` / `ADMIN_PASSWORD`** задают клиента **Kafka (SASL)** для контейнеров, это **не** логин администратора HTTP. Логин в UI задаётся при **`bootstrap-admin`** или уже лежит в SQLite воркера `user_management`.

### `make tests` «залипает» или ходит в Kafka локально?

Для локальных целей Makefile сбрасывает переменные смежной шины. Если запускаете pytest вручную с выставленным `UAS_ADJACENT_BUS_INTEGRATION=1` без брокера, поведение отличается — см. [`README.md`](README.md).

### Где описание межсистемной интеграции?

[`integration_tasks.md`](integration_tasks.md).

### Откуда брать версии Python/tooling?

Стек ориентирован на **Python 3.12+** и указания в корневом `config/`; см. также ограничения Node для фронта в выводах `npm` при сборке web.
