## 2. Назначение и границы

Система обеспечивает учебный контур **разработчика БАС**: учёт пользователей (роли), приём и метаданные прошивок, сертификация (в т.ч. заглушка регулятора), реестр дронов, покупка эксплуатантом, аудит и опциональная отправка событий во внешний журнал. Целевой режим исполнения: **отдельные Docker-контейнеры на домен**, обмен через **брокер** и **security monitor**, политики в `shared.security_policies`. Допускается учебный режим **sqlite** (монолитный контекст в процессе шлюза) без брокера на пути вызова.

## 3. Нотация диаграммы архитектуры политики (ДАП)

ДАП отражает уровни доверия **функциональных доменов** и логические допустимые потоки между ними (без отображения монитора и брокера на самой ДАП). Уровни:

1. **Недоверенный (НДБ)** — нет явного обоснования прямой критичности ≥ одной **официальной ЦБ** на диаграмме; исходящие с НДБ — низкоцелостные; входящие — по согласованию с политикой.
2. **Повышение целостности (жёлтый)** — домен критичен ≥ одной ЦБ и имеет ≥ одну «красную» входящую дугу на ДАП.
3. **Полностью доверенный контур данных (ДДБ в модели данных)** — критичное состояние ЦБ/ТБ в **SQLite внутри границы** домена; на ДАП отдельным узлом «БД» не выделяется.

Канонические **ЦБ-1…ЦБ-3** и **ТБ** — только в формулировках [`README.md`](README.md) §1. Детализация цветов узлов и стрелок на ДАП — [`README.md`](README.md) §2.

## 4. Базовые требования к системе (БТС)

| ID | Требование |
|----|------------|
| БТС1 | Несколько доменов безопасности, если иное не обусловлено архитектурой. |
| БТС2 | Взаимодействие между доменами — через брокер и проверку **монитором безопасности** по политикам (в учебном sqlite-режиме — эквивалентная логика в процессе шлюза без отдельного брокера на пути). |
| БТС3 | Перечислены активы, цели и предположения безопасности, уровни доверия доменов (документировано в README, ДАП, integration_tasks). |
| БТС4 | Автоматизированные тесты проверки политик безопасности. |
| БТС5 | Код доверенных доменов — покрытие тестами **≥ 60 %** (целевые пороги уточнять в `requirements_spec` / практике проекта). |
| БТС6 | Код доменов, повышающих целостность, — **≥ 70 %**, включая зависимости, где применимо; запрет известных уязвимых зависимостей в доверенном контуре; учебные исключения — со статическим анализом/БДУ по согласованию. |
| БТС7 | Недоверенные домены — **≥ 30 %** без учёта зависимостей. |
| БТС8 | Выдача целей безопасности / сертификата по запросу (модель с подписью регулятора — по сценарию прототипа). |
| БТС9 | Выдача событий безопасности по запросу (через аудит / API). |
| БТС10 | Передача телеметрии в сервис аналитики (опционально, `DroneAnalytics`). |
| БТС11 | Передача событий безопасности в аналитику (через `audit_log` → `analytics_adapter`). |
| БТС12 | Сертификат безопасности системы с указанием целей — применимо к учебной модели; инфраструктура (брокер, сторонние СУБД) может быть вне сертификационного контура. |
| БТС13 | События журналируются с уровнем критичности. |

## 6. Основные функции (ОФ)

| ID | Описание |
|----|----------|
| ОФ1 | Создание/конфигурация дрона (тип, компоненты, цели безопасности) в рамках прототипа. |
| ОФ2 | Сертификация прошивки у «Регулятора» с указанием целей безопасности. |
| ОФ3 | Регистрация дрона с сертифицированной прошивкой и целями. |
| ОФ4 | Веб-интерфейс: прошивки, сертификаты, дроны; отображение ЦБ, стоимости/метрик учебной модели. |
| ОФ5 | Скрипты/процедуры запуска сертификации (`make`, HTTP API). |
| ОФ6 | Веб для эксплуатанта: витрина и покупка. |

**Роли:** администратор (CRUD пользователей), разработчик (прошивки, сертификация, реестр), эксплуатант (витрина, покупка).

**Веб (итерация 2):** JWT `Authorization: Bearer`, каркас с сайдбаром и настройками темы (тёмная по умолчанию), Nuxt, nginx reverse proxy, порт из окружения (`HTTP_PORT`). E2E: Playwright, `make e2e-test`, `E2E_BASE_URL`.

**Расширенная функция:** **РФС1** — интеграция с `systems/DroneAnalytics`, управляется переменными окружения (`DRONE_ANALYTICS_ENABLED` и др., см. README).

## 8. Организационные требования к коду

- Стиль: PEP 8; принципы SOLID; осмысленные docstrings; комментарии на русском для нетривиальной логики.
- Цикломатическая сложность функций — не выше **5** в новом коде (ориентир; отклонения фиксировать в ревью).
- Тесты: `pytest`, unit / module / integration / e2e по необходимости.
- Ограничение репозитория: по умолчанию изменения в **`systems/uas_dev_company`**; правки других систем — только по явному согласованию ТЗ.

## 9. Архитектура данных и изоляция

- **Per-domain SQLite:** каталог `UAS_DOMAIN_DATA_ROOT/<domain_id>/data.sqlite3`, инициализация `make init-data`, см. [`architecture_variants.md`](architecture_variants.md).
- **Узкие образы воркеров**, отдельные тома, анализ COPY и НДБ-носителей в метриках ДВБ — README §2.1, `architecture_variants.md`, `tcb_metrics.json` (`task24_copy_ndb_carrier`).
