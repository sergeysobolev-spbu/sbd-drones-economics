
# Варианты хранилища по доменам

Сравнение подходов к размещению состояния доменов **UAS Dev Company** при требовании «один функциональный домен — изолированная зона хранения».

## Вариант A — полная независимость (реализовано)

| Критерий | Оценка |
|----------|--------|
| Изоляция ДВБ | У каждого домена с состоянием — **свой** каталог виртуальной ФС и **свой** файл SQLite только с таблицами этого домена (`UAS_DOMAIN_DATA_ROOT/<domain_id>/data.sqlite3`). |
| Целостность | Авторизация и проверки целостности выполняются владельцем данных; нет скрытых SQL-JOIN между доменами. |
| Междоменность | Только через **security_monitor** (`proxy_request` + расширенный allow-list в `shared.security_policies`). |
| Саги | Регистрация, сертификация, покупка, реакция на уязвимость — цепочки вызовов с явными шагами; идемпотентность там, где заложена в доменах (например `correlation_id` у Регулятора). |
| Миграция | Базы **только greenfield**; перенос из старой монолитной SQLite **не** выполняется. |
| Эксплуатация | Несколько файлов на общем volume; резервное копирование по доменам; `make init-data` создаёт каталоги. |

## Вариант B — «две базы»: доверенная SQLite + НДБ для некритичных

Идея из текста ТЗ: узкий круг доменов (контур ДВБ/ЦБ) в **одной** доверенной SQLite; **остальные** домены и **низкоцелостные / некритичные для ЦБ** данные — во **второй** SQLite (НДБ).

| Критерий | Оценка |
|----------|--------|
| Плюсы | Меньше файлов; проще одномоментный бэкап «всего критичного» одним файлом. |
| Минусы | Риск **смешения** данных разной критичности в НДБ; усложнение политик «что где лежит»; саги всё равно нужны, если критичный контур логически разделён по процессам. |
| ДВБ | Граница доверия размывается: одна «НДБ-БД» на много типов данных повышает риск неверной классификации при эволюции ТЗ. |

## Выбор архитектора

**Принят вариант A (полная независимость)** по решению архитектора: явное соответствие «один домен безопасности — одна зона хранения», проще аргументировать ДВБ и междоменный контроль через монитор. Вариант B зафиксирован как **отклонённая** альтернатива из-за риска смешения уровней целостности в общей НДБ-SQLite.

См. также: `docs/README.md` §3.1, `shared/domain_storage.py`, `shared/storage.py`.

## Изоляция образов и томов

Сравнение **до** и **после** с точки зрения стоимости ДВБ и утечки недоверенного кода/данных между доменами.

### Было (до сужения образов и раздельных томов)

| Аспект | Состояние |
|--------|-----------|
| Слои образов | Девять backend-образов собирались с **`COPY systems/uas_dev_company`** — в каждый процесс попадали **все** каталоги `src/*`, тесты, документация и пр. в пределах дерева. |
| ДВБ | В аттестацию «целевого» ДДБ-контейнера формально попадал **чужой** код (в т.ч. НДБ-домены), что раздувает объём доверия и стоимость обоснования. |
| Данные | Один том `…/resources` монтировался в шлюз и воркеры — в контейнере была видна **вся** `resources/domains/**` и потенциально чужие `data.sqlite3`. |
| Риск для НДБ | Процессы **audit_log** / **analytics_adapter** получали тот же mount-point, что и воркеры ЦБ-контура; на уровне ОС возможен доступ к чужим файлам БД вне намеренной логики IPC. |

### Стало (после сужения образов и раздельных томов)

| Аспект | Состояние |
|--------|-----------|
| Образы воркеров | Общий **`docker/worker.Dockerfile`** с `build-arg DOMAIN`: в образе **один** пакет `src/<домен>` + whitelist **`shared`**, плюс **`sdk`** и **`broker`**. Корневой **`.dockerignore`** уменьшает контекст монорепозитория. |
| Шлюз bus | **`src/gateway/docker/Dockerfile`**: только `gateway` (без **`sqlite_context.py`**) и минимальный **`shared`** для JWT, моделей, `journal_bootstrap`, шины. Режим **`UAS_GATEWAY_BACKEND=sqlite`** — отдельный толстый образ **`Dockerfile.sqlite`** (профиль **`sqlite-dev`**), не смешивается в метриках union с узким шлюзом. |
| **security_monitor** | Минимальный набор модулей (политики + IPC в audit), без **`worker_deps`** и без доменных пакетов. |
| Тома | У каждого воркера свой **named volume** только на `resources/domains/<domain_id>`; у **`api_gateway`** (bus) томов **нет**; эталон «без данных доменов» — как у **`security_monitor`**. |

### Связь с ДВБ

Сужение FS в образе и разделение томов **не заменяет** модель «контейнер целиком в ДВБ при ЦБ», но уменьшает **избыточный** объём кода и данных в сертификационном контуре и снижает риск **ненужных** зависимостей между НДБ и данными ЦБ на уровне хоста.

## Метрики ДВБ по фактическому COPY и «НДБ в образе ЦБ»

Ниже — варианты доработки скриптов оценки ДВБ, покрытия тестами и сборки узких образов. Выбор записан явно («рекомендация для прототипа»); актуальная реализация — в `scripts/tcb_metrics.py`, `scripts/parse_uas_docker_copy.py` и связанных тестах.

### 1. Связка Dockerfile ↔ множества путей для SLOC (`python_path_specs`)

| Вариант | Плюсы | Минусы |
|---------|-------|--------|
| **A. Ручные списки + unit-тест сравнения с парсером COPY** (как сейчас при узких образах воркеров, плюс автоматический drift-тест) | Предсказуемость; простая отладка; метрики читаются из кода без запуска разбора Dockerfile. | Два источника: при добавлении `COPY` нужно помнить и список, и Dockerfile. |
| **B. Dockerfile как единственный источник: списки генерируются парсером при каждом `tcb_metrics`** | Нет расхождения; аттестационный охват точно следует сборке образа. | Парсер должен понимать все конструкции `COPY`; сложнее тестировать edge cases без golden-файлов. |
| **C. Переход на `pip install -e ./pkg` или single wheel в образах** и учёт установленных артефактов | Одна упакованная декларация для рантайма и метрик. | Большая переработка Dockerfile/compose учебной системы. |

**Рекомендация для текущего репозитория:** начать с **варианта A**: парсер COPY + автоматический **fail** расхождения парсера и `SHARED_*_SCOPE`/`python_path_specs`; при желании второй шагом сузить код до подходов **B** для воркеров, оставив ручную корректировку только там, где парсер не выражает смысл (например, профиль sqlite-dev исключён из union явно).

### 2. Жёсткость при рассинхроне Dockerfile и метрик

| Вариант | Плюсы | Минусы |
|---------|-------|--------|
| **Строгое падение в CI/`make tcb-metrics`** | Невозможно «тихо» разойтись при ревью. | Ложные срабатывания при осознанной правке Dockerfile до обновления списков. |
| **Предупреждение и запись во `tcb_metrics.json`** без кода ошибки | Мягкая миграция. | Легко пропустить и аттестовать «не ту» поверхность. |

**Рекомендация:** **строгая проверка** в режиме, используемом для отчётов (`--target`/CI); для локальных экспериментов допускать флаг «только предупреждение» при необходимости (явно в коде скрипта).

### 3. Классификация «НДБ-носитель попал в образ ДДБПЦД для ЦБ»

| Вариант | Плюсы | Минусы |
|---------|-------|--------|
| **Отдельный JSON/таблица ролей модулей** (`tb_ndb_carrier`, `cb_core`, …) | Явное сопоставление со смыслом ДАП/§2; удобно для отчётов аудита. | Поддержка списка при изменении shared. |
| **Только эвристики по имени пути** без явной таблицы | Быстро. | Ложная классификация смешанных модулей. |
| **Пометки в коде (например, коммент-тег `# tcb:classify=...`)** | Рядом с реализацией. | Засоряет производственный код; инструменты не стандартны. |

**Рекомендация:** файл рядом со скриптами (JSON или маленький Python-константный модуль) + **пересечение** с множеством файлов из п. 1 для метрик пересечения и для отчёта покрытия.

### 4. Выравнивание `pytest-cov` с содержимым образов ЦБ

| Вариант | Плюсы | Минусы |
|---------|-------|--------|
| **Явный широкий `--cov=` в Makefile** + тест «каждый `.py` из union образов ЦБ попадает под один из включённых пакетов» | Совместимо с текущим `pipenv`; не ломает привычные команды. | Список пакетов может разрастись; тест ловит пропуски. |
| **Генерация `.coveragerc` или аргументов pytest из парсера COPY** | Минимальный реальный охват. | Сложнее отлаживать локально; нужен стабильный генератор. |

**Рекомендация:** оставить **Makefile** как «человекочитаемый коммитимый» слой, добавить **проверочный тест** на полноту покрытия union’а файлов для `in_cb123_tcb_union` (и при необходимости отдельно для всех `whole_domain_in_tcb`).

### 5. Перспектива сборки: уменьшение «эффективной ДВБ» в образе

| Вариант | Плюсы | Минусы |
|---------|-------|--------|
| **`--build-arg SHARED_PROFILE=minimal|full` в `worker.Dockerfile`** | Один Dockerfile; разные теги для демо и для «узкого» контура. | Усложнение матрицы образов и compose. |
| **Два Dockerfile воркера** (узкий / полный) | Ясная линия в ревью и в SBOM. | Дублирование; риск расхождения базовых слоёв. |
| **Вынести ТБ/НДБ-хелперы в отдельный пакет**, не копируемый в воркеры ЦБ-1…3 | Минимальный объём доверия в аттестации ЦБ. | Рефакторинг импортов и политик «что доступно воркеру». |

**Рекомендация:** в ближайшем цикле зафиксировать **учёт и отчётность** (что именно в образе); параллельно спланировать **профиль `minimal` shared** для воркеров ЦБ без кардинального разрыва демо compose.

### Сборная рекомендация (кратко)

1. Метрики и отчёты должны опираться на **фактический COPY** с **жёсткой проверкой** совпадения с декларацией в `tcb_container_domains.py` (вариант **1A + 2 strict**).  
2. Классификация «НДБ в образе ЦБ» — **явный список ролей** (вариант **3, JSON/константы**), не только эвристики.  
3. Покрытие — **текущий Makefile + тест полноты** (вариант **4, проверочный тест**).  
4. Сужение образов — **поэтапно**, через **build-arg профили** (вариант **5, первый шаг**), с отдельной фиксацией в метриках при появлении второго профиля.

См. также: `docs/tcb_assessment.md`, `docs/README.md` §2 (ДАП: узел ≈ контейнер; политика монитора не дублирует внутрипроцессный SQLite), `scripts/tcb_container_domains.py`, `docker/worker.Dockerfile`.
