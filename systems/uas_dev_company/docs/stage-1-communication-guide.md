# Stage 1 — руководство по межсистемной коммуникации (концепция и миграция)

Документ фиксирует **целевую модель обмена (Stage 1)**: Регулятор выдаёт (по запросу) имена топиков всех авторизованных смежных систем (эксплуатанты, дронопорты, агрегаторы, ОРВД, БАС/дроны, НУС и др.), допускается обмен только с участниками **белого списка** Регулятора, доступ к топикам — **учётными данными с разграничением чтение/запись**, множественные экземпляры смежных систем с **идентификатором, сертифицированным Регулятором**, используемым как префикс в пространстве имён топиков.

**Код систем в этом шаге не меняется** — здесь только концепция, обзор текущей реализации и пошаговый план миграции.

Связанные материалы: [`topic_namespaces.md`](topic_namespaces.md), [`integration_tasks.md`](integration_tasks.md), реализация топиков в `src/shared/topics.py`, шина — пакет `broker` (`SystemBus`).

---

## 1. Целевая концепция Stage 1

### 1.1. Регулятор как доверенный источник топологии обмена

- По запросу доверенного клиента (например, разработчик БАС после аутентификации у Регулятора) выдаётся **машиночитаемый каталог топиков** (или правил генерации имён топиков) для всех **авторизованных** смежных систем, с которыми разрешено взаимодействие в текущем контексте (тенант, регион, версия контрактов).
- Для каждого участника в каталоге указываются как минимум: **тип системы** (оператор, дронопорт, агрегатор, ОРВД, БАС, НУС, …), **экземплярный идентификатор**, ссылка на **сертификат допуска** Регулятора, **режим допустимых операций** (чтение/запись по классам топиков).
- Обмен между двумя системами технически возможен только если пара **явно разрешена политикой Регулятора** (белый список пар «кто может говорить с кем» и с какими намерениями), а клиент имеет учётную запись с правами ACL брокера, согласованными с этим разрешением.

### 1.2. Множественность экземпляров и префиксы

- Исключение — один логический **Регулятор** в модели допусков; все остальные типы могут иметь **много независимых установок**.
- Каждая установка имеет стабильный **system_id**, выданный при сертификации интеграции с общей средой сообщений (не путать с бизнес-идентификаторами вроде регистрации БАС).
- **Префикс топика** включает `system_id` (или производное от него согласованное правило хэширования/неймспейса), чтобы топики разных эксплуатантов, двух разных ДронAnalytics и т.д. не пересекаются случайно.

### 1.3. Защита доступа к топикам

- На уровне брокера: **аутентификация клиента**, **ACL по топику** с разделением **Read / Write** (в терминологии Kafka — `READ`/`WRITE` на ресурс `Topic`; для MQTT — эквивалентные ограничения подписок и публикаций).
- На уровне приложения (как усиление): сохранить или развить **явные политики** (например, паттерн «запрос только через монитор домена» во `uas_dev_company`), но **Stage 1** требует, чтобы без соответствующих прав брокера сообщение объективно не ушло получателю.

## 2. Анализ текущей реализации обмена (учебный контур)

### 2.1. Именование топиков

| Слой | Назначение | Реализация |
|------|------------|------------|
| Внутри `uas_dev_company` | Домены/воркеры, шлюз, монитор | Топики `components.<имя>`; опционально префикс из `SYSTEM_NAMESPACE` — см. `component_topic()` в `topics.py`. |
| Публикация системы как целого | Общая «внешняя» витрина | `system_topic()` → `systems.uas_dev_company` (с тем же необязательным префиксом). |
| Смежные системы в коде | Регулятор, оператор, дронопорт, журнал | Класс `ExternalTopics`: фиксированные имена **`systems.regulator`**, **`systems.operator`**, **`systems.drone_port`**, **`systems.drone_analytics`** — один канонический топик **на тип**, без суффикса экземпляра. |

Документировано в [`topic_namespaces.md`](topic_namespaces.md).

### 2.2. Паттерн сообщений и доверие

- Абстракция **`SystemBus`**: сообщения-словари с `action`, `sender`, `payload`, поддержка **`request/reply`** и `correlation_id` — см. `broker/src/system_bus.py`.
- В **Kafka-профиле** compose задаются общие переменные `BROKER_USER` / `BROKER_PASSWORD` для клиентов; это **общая учётная запись брокера** для всех контейнеров учебной системы, а не пер-топичные ACL как в задаче Stage 1.
- **Междоменный доступ внутри `uas_dev_company`** ограничен **`security_monitor`** и политикой `shared.security_policies`: allow-list по парам топиков/действий (ДВБ). Это политика **приложения**, а не реестр топиков Регулятора и не Kafka ACL для внешнего оператора-префикса.

### 2.3. Интеграция с «типами» смежных систем

- На шине смежность моделируется адаптерами в `shared/bus_integration_adapters.py`: запросы к Регулятору, оператору, дронопорту, DroneAnalytics идут на строки топиков из `ExternalTopics.*()`.
- В интеграционных тестах и моках (`tests/integration/bus_adjacent_mocks.py`) подписчики висит именно на этих именах — что подтверждает модель **«одна шина — одно общее имя на тип системы»** в текущем прототипе.

### 2.4. Связь с дорожной картой из `integration_tasks.md`

Там уже зафиксированы версионируемые контракты, корреляция, идемпотентность (`INT-NFR-*`), перечень смежных ролей. По сравнению с целями Stage 1 (§1) **не хватает** следующего явного слоя:

- централизованной **выдачи каталога топиков по запросу**;
- **множественных экземпляров с префиксами** для каждого типа системы кроме Регулятора;
- **тонких ACL чтение/запись** по топикам, выровненных с белым списком Регулятора.

## 3. Разрыв между текущей моделью и Stage 1

| Аспект | Сейчас | Stage 1 (цель) |
|--------|--------|----------------|
| Имена топиков внешних систем | Одно имя на тип (`systems.operator`, …). | Экземплярное ветвление: `systems.<type>.<system_id>...` или согласованный иерархический префикс. |
| Источник правды по списку тем | Константы в коде (`ExternalTopics`). | Каталог/реестр от Регулятора + локальный кеш с TTL и подписью/версией. |
| Кто может отправлять во внешний топик | Политики домена + наличие брокерной учётки среды. | Белый список пар + ACL брокера под сервисный principal этой установки. |
| Разграничение R/W на брокере | Практически не моделируется (общий пользователь окружения). | Отдельные principals или ограниченные ACL на подмножество топиков. |
| Сертификация смежной системы | Обсуждается в интеграционных задачах, но не связана с префиксом топика. | `system_id` и область топиков — следствие сертификата интеграции Регулятора. |

## 4. Пошаговый план миграции на новую модель (без привязки к конкретному спринту)

Этапы согласовываются между владельцами Регулятора, БАС, брокера и каждого класса смежных систем.

### Этап A — Инвентаризация и каноническая схема имён

1. Зафиксировать **глобальный корень именования**: например `<namespace>/systems/<regulated_type>/<system_id>/…` совместимо с уже используемым `SYSTEM_NAMESPACE` для изоляции стендов.
2. Перечислить все классы смежных систем из цели Stage 1 (§1.1) и добавить резерв под новые типы.
3. Описать **минимальный набор топиков на тип** (команды, события, ответы) и правило **reply-топиков** (не ломать `correlation_id` / request-reply).

### Этап B — Контракт Регулятора «каталог топиков»

1. Ввести API/действие (шина или REST): **«выдать каталог авторизованных топиков»** для текущего запросившего клиента (`system_id`, роль интеграции, версия схемы).
2. В ответ включать **белый список** разрешённых целевых `system_id` и для каждого — маски топиков и разрешённые операции (**read/write**).
3. Версионировать ответ (`schema_version`, хэш конфигурации) для воспроизводимости и аудита.

### Этап C — Политики брокера

1. Вынести из compose «единый пароль на всех» в сторону: **учётная запись на установку** (или на процесс домена) с ACL **только** на свой префикс и явно разрешённые удалённые префиксы (по результату каталога).
2. Включить **запись** только там, где в каталоге разрешено `write`; подписка — там, где разрешено `read`.
3. Определить процедуру **отзыва**: Регулятор помечает сертификат / интеграцию → каталог истекает → клиент перезапрашивает; брокерные ACL синхронизируются автоматией (оператор кластера) или через интеграцию с тем же источником правды.

### Этап D — Эволюция прикладных адаптеров

1. Заменить использование голых констант `ExternalTopics.operator()` на **конфигурацию экземпляра**, заполняемую из каталога Регулятора (или из локальной мапы в переходный период).
2. Сохранить **обратную совместимость** на один переходный период: поддержка режима «наследие — один топик на тип» и режима «полный системный префикс».

### Этап E — Проверка и поэтапное включение

1. Прогнать сценарии из [`integration_tasks.md`](integration_tasks.md) против стенда с ACL и множественными mock-операторами/дронопортами на разных `system_id`.
2. Измерять отказы безопасности: попытки публикации во внешний префикс без строки в каталоге или без прав **write**.
3. Документировать в [`topic_namespaces.md`](topic_namespaces.md) финальную схему и отличия Stage 0 / Stage 1.

---

## 5. Краткое резюме

Текущий учебный стек уже разделяет **внутренние компоненты** (`components.*`) и **смежные системы** (`systems.*`), прикладывает **политику монитора** внутри `uas_dev_company` и использует **общий брокерный логин** среды. **Целевая архитектура Stage 1** добавляет уровень **Регулятор-ориентированного каталога топиков и белых списков**, **экземплярные префиксы** для всех типов смежных систем кроме Регулятора и **действующие ACL с разделением чтение/запись**. Переезд на эту модель целесообразно вести по этапам A–E, не ломая сразу контракты действий сообщений из `integration_tasks.md`, а добавляя к ним слой имён топиков и прав доступа.
