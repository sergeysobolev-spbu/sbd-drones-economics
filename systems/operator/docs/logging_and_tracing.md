# Журналирование и сквозная трассировка (trace_id/span_id/parent_span_id)

Документ описывает единые правила наблюдаемости для системы **Эксплуатант** (`systems/operator`): какие поля должны присутствовать в сообщениях, как формируются `trace_id/span_id/parent_span_id`, и как читать логи при отладке сценариев.

## 1. Термины

- **trace_id**: идентификатор сквозной «цепочки» операций (например, обработка заказа от Агрегатора до резервирования БАС).
- **span_id**: идентификатор конкретного шага внутри трассы (обработка сообщения, вызов компонента и т.п.).
- **parent_span_id**: ссылка на «родительский» span, чтобы восстанавливать дерево вызовов.

## 2. Формат сообщения в шине

Минимальный ожидаемый формат (поля могут дополняться):

```json
{
  "action": "receive_order",
  "payload": { "...": "..." },
  "sender": "operator-01",
  "timestamp": 1710600000.123,
  "trace_id": "…",
  "span_id": "…",
  "parent_span_id": "…"
}
```

Правило: **трассировочные поля находятся на верхнем уровне сообщения**, а не внутри `payload`.

## 3. Правила формирования и прокидывания трассы

Источник истины — `sdk/base_component.py`:

- При входящем сообщении компонент извлекает контекст из `trace_id/span_id/parent_span_id`.
  - Если полей нет, создаётся новый `TraceContext` (новый `trace_id`).
- Для обработки конкретного `action` создаётся **дочерний span**:
  - `trace_id` сохраняется,
  - `span_id` генерируется заново,
  - `parent_span_id` указывает на `span_id` входящего контекста.
- Для исходящего запроса/события создаётся **дочерний span** от текущего контекста и добавляется в сообщение.

Таким образом:

- `trace_id` остаётся **одним и тем же** по всей цепочке.
- `span_id` меняется на каждом шаге.
- `parent_span_id` позволяет восстановить дерево «кто кого вызвал».

## 4. Где в коде это реализовано

- `sdk/base_component.py`
  - `TraceContext` (создание/дочерние spans)
  - `_handle_message()` (создание span для обработчика)
  - `create_message()` (инъекция контекста в исходящее сообщение)
- `systems/operator/src/operator_system.py`
  - при обработке внешних запросов создаёт `TraceContext.from_message(message)`
  - передаёт контекст во внутренние запросы через `_request_component(..., trace_context=...)`

## 5. Рекомендации по чтению логов

1. Возьмите `trace_id` из сообщения/ответа или из логов компонента-инициатора.
2. Отфильтруйте логи по `trace_id`.
3. Для восстановления последовательности:
   - группируйте события по `parent_span_id → span_id`;
   - начинайте с корневого span (у него `parent_span_id` обычно пустой/`null` или отсутствует в самом первом сообщении).

## 6. Требование к тестам

Системные интеграционные/сквозные тесты должны:

- задавать `trace_id` на входе сценария (или принимать автоматически созданный),
- проверять, что при межкомпонентных вызовах `trace_id` сохраняется,
- при необходимости проверять, что `parent_span_id` меняется и не теряется (цепочка spans строится).
