# Сценарии сквозных тестов модели 

## Инструменты и форматы данных

### Оптимальный вариант протоколов интеграции (стандарты + тестируемость + сертификация)

Цель набора протоколов ниже — обеспечить:
• наблюдаемость E2E (все сообщения трассируются и коррелируются),
• формализацию контрактов (схемы/версии),
• воспроизводимые артефакты для аудита и сертификации.

#### Сквозные требования (идентификация, корреляция, безопасность)

▎Идентификаторы (везде)

• mission_id, operation_id (например: AGR|INSP|CARGO)
• uas_id, gcs_id, operator_id
• order_id, permit_id, policy_id, port_slot_id

▎Корреляция

• trace_id/span_id по W3C Trace Context
  – HTTP заголовки: traceparent, tracestate

▎Безопасность

• mTLS между backend-компонентами (агрегатор, эксплуатант, дронопорт, страховая, UTM-шлюз)
• OAuth 2.1 (обычно client_credentials) для API
• Подпись критичных событий (аудит/комплаенс): JWS или detached signature в поле sig

▎Время

• синхронизация NTP (минимум) или PTP (желательно для испытаний)
• время в UTC формате RFC3339Nano

---

#### Рекомендуемые протоколы по стыкам (интеграционная “карта”)

▎1) Агрегатор ↔ Эксплуатант

• HTTPS REST + JSON с контрактом OpenAPI 3.1
• события: Webhook (ретраи + идемпотентность через Idempotency-Key)
• шина событий/аудит: CloudEvents 1.0 поверх NATS JetStream или Kafka

▎2) Эксплуатант/НУС ↔ БВС (C2/телеметрия)

• команды: MAVLink2 (желательно с защищённым транспортом, например WireGuard)
• телеметрия наружу: MQTT 5.0 поверх TLS
  – топики: uas/{uas_id}/telemetry, uas/{uas_id}/health, mission/{mission_id}/events

▎3) UTM/ATM (планы/разрешения/ограничения/динамические геозоны)

• API-стиль по мотивам ASTM F3548 (UTM/USS): operational intent, permit, constraints, dynamic geofence
• Remote ID (если применимо): ASTM F3411 (broadcast/network)

▎4) Регулятор/реестр сертификатов (валидность/отзыв)

• OCSP (RFC 6960) или REST “certificate status”
• кэширование с TTL + логирование факта проверки в REG_STATUS

▎5) Страховая

• HTTPS REST + JSON для привязки полиса к mission_id
• клейм-пакет: application/zip с manifest.json + вложения (логи/хэши)

▎6) Дронопорт

• операции: HTTPS REST + JSON (слоты, доступ, подтверждения)
• события: MQTT 5.0 (“дверь открыта”, “груз установлен”, “замок закрыт”, “заряд завершён”)

---

▎2) Формат журналов и артефактов (унификация под E2E и аудит)

#### Форматы файлов

• события: *.jsonl (JSON на строку)
• телеметрия: *.parquet (предпочтительно) или *.csv (упрощённо)
• команды НУС: GCS_CMD.jsonl
• сеть (опционально): *.pcapng
• доказательная целостность: AUD_HASH.jsonl + sha256sums.txt

#### Рекомендуемые “семейства” артефактов

▎Базовые (для всех операций)

• AGG_EVT, OPS_EVT, GCS_CMD, UAS_TLM, UAS_HLTH, PORT_EVT, UTM_MSG, REG_STATUS, INS_POL, INS_CLM (при инцидентах), AUD_HASH

### Комплекты тест-кейсов (E2E + негативные + инциденты + комплаенс)

#### Общие метрики/пороги (рекомендованные)

• telemetry_gap_seconds_max ≤ 5 c (для INSP и CARGO лучше ≤ 2 c)

• T_detect (обнаружение отказа): ≤ 5 c (AGR), ≤ 2 c (INSP), ≤ 3 c (CARGO)
• T_abort_initiate (от REG_STATUS=REVOKED до прерывания): ≤ 5 c
• T_land_mode_engage (до включения аварийной посадки): ≤ 10 c
• geofence_violation_count = 0

## Переработанные рекомендации для учебного проекта

▎1) Обновлённые рекомендации по интеграции (учебный проект, всё через Mosquitto/Kafka)

▎1.1. Базовая идея: “интеграция через брокер” + конструктивная ИБ

Все взаимодействия делаем сообщениями (publish/subscribe). Чтобы показать принципы ГОСТ Р 72118-2025 (изоляция доменов, контроль взаимодействия, минимизация доверенной базы), архитектуру лучше строить так:

1) Разделить систему на домены безопасности (каждый — отдельные процессы/контейнеры/сети/учётки).  
2) Любой обмен между доменами — только через контролируемую “точку медиации” (междоменный шлюз).  
3) Всё критичное для целей безопасности свести к малому набору компонентов (TCB) и сделать его проще (конфиги, минимум кода, проверяемость).

---

▎1.2. Предлагаемое разбиение на домены безопасности (упрощённо)

Домен D1_FLIGHT (полёт/БВС):  
• uas-sim (симулятор БВС)
• gcs-sim (симулятор НУС/оператора)

Домен D2_OPS (эксплуатант/операции):  
• ops-core (управление миссией, состояние)
• ops-policy-enforcer (решение “можно/нельзя” для команд старта/продолжения)

Домен D3_EXTERNAL (внешние прототипы):  
• utm-sim (permit/геозоны)
• registry-sim (статус сертификата: VALID/REVOKED)
• insurance-sim (полис: ACTIVE/EXPIRED)
• droneport-sim (слоты/события)

Домен D0_MEDIATION (междоменная медиация — ключевой для ИБ):  
• interdomain-gateway (единая точка контроля междоменных сообщений: ACL + валидация + маршрутизация + журналирование)
• audit-log (неизменяемый журнал/хеш-цепочка — можно упрощённо)

---

▎1.3. Как использовать брокеры, чтобы реально показать “изоляцию доменов”

Есть два учебно-практичных варианта; можно выбрать один.

Вариант A (нагляднее для доменной изоляции): несколько брокеров + мост/шлюз
• Отдельный Mosquitto/Kafka на домен: broker_d1, broker_d2, broker_d3
• Между ними нет прямых мостов, только через interdomain-gateway (он подписывается на “внешний” и публикует во “внутренний” по правилам).
• Плюсы: понятная демонстрация изоляции, проще обосновать TCB.
• Минусы: чуть больше DevOps.

Вариант B (проще развернуть): один брокер + строгие namespaces/ACL
• Один Mosquitto/Kafka
• Топики строго разделены по доменам, пользователи доменов имеют минимальные права.
• interdomain-gateway — единственный субъект, у которого есть права “читать из D3_* и писать в D2_*”, “читать из D2_* и писать в D1_*” и т.п.
• Важно: прямые права доменов друг к другу запрещены ACL.

Для учебного проекта чаще оптимален B, но A лучше демонстрирует “жёсткие границы”.

---

▎1.4. Минимальная доверенная вычислительная база (TCB) под цели безопасности

Чтобы выполнить “минимизация и упрощение TCB”, явно фиксируем:

TCB (минимум):
• broker (конфигурация аутентификации/авторизации/ACL, TLS)
• interdomain-gateway (маленький код: только проверка/маршрутизация/логирование)
• ops-policy-enforcer (простые правила допуска команд)
• key-store/секреты (хотя бы файловые ключи/пароли в docker secrets)
• audit-log (упрощённый append-only лог + хеширование)

Не TCB (может быть “недоверенным”, но контролируемым):
• utm-sim, insurance-sim, registry-sim, droneport-sim, aggregator-ui и т.п.
Их сообщения никогда не принимаются “как есть”: только через шлюз и только по схеме/правилам.

---

▎2) Единый формат сообщений (контракты) для MQTT/Kafka

▎2.1. Конверт сообщения (упрощённый CloudEvents-подобный)

Рекомендуется единый “envelope”, чтобы проще тестировать и валидировать.

{
  "msg_id": "b6b3c2a3-7c8f-45a8-9c0a-0a8e3c8c2f6a",
  "ts": "2026-03-06T12:34:56.123Z",
  "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736",
  "source": "utm-sim",
  "domain": "D3_EXTERNAL",
  "type": "PERMIT_ISSUED",
  "schema": "v1.permit.issued",
  "ttl_ms": 60000,
  "data": { "mission_id": "MIS-001", "permit_id": "PERMIT-77", "valid_from": "...", "valid_to": "..." },
  "sig": "base64(signature_over_canonical_json)"
}


Минимум для учебного проекта:
• msg_id + ttl_ms (анти-replay на уровне приложений)
• schema (версионирование)
• sig только для критичных событий (например REG_STATUS, PERMIT, POLICY)

---

▎2.2. Топики/каналы (шаблон)

Чтобы не усложнять, достаточно разделить на cmd и evt и домен.

Для MQTT (пример):
• v1/D2_OPS/cmd/mission.start
• v1/D1_FLIGHT/evt/telemetry
• v1/D3_EXTERNAL/evt/permit
• v1/D0_MEDIATION/evt/gateway.decision

Для Kafka (пример):
• v1.d2_ops.cmd
• v1.d1_flight.evt
• v1.d3_external.evt
• v1.d0_mediation.audit

▎3) Упрощённые механизмы безопасности (достаточно для демонстрации)

▎3.1. На уровне брокера (обязательный минимум)

Mosquitto:
• TLS (можно самоподписанные сертификаты) + username/password
• ACL: доменам запрещено читать/писать “чужие” топики
• interdomain-gateway имеет расширенные права (строго по маршрутам)

Kafka:
• TLS + SASL/SCRAM
• ACL на топики по принципу минимальных привилегий

▎3.2. На уровне приложений (контроль взаимодействий)

• interdomain-gateway делает:
  – валидацию schema (JSON Schema)
  – проверку ttl_ms и msg_id (replay-cache на 5–10 минут)
  – (опционально) проверку sig для критичных типов
  – нормализацию полей и логирование решения “пропущено/заблокировано” в D0_MEDIATION

• ops-policy-enforcer делает:
  – перед выпуском MISSION_START в D1_FLIGHT проверяет:
    ▪ REG_STATUS == VALID
    ▪ INS_POL == ACTIVE (для CARGO обязательно, для AGR/INSP можно “опционально”)
    ▪ наличие PERMIT и окно времени
  – при смене REG_STATUS -> REVOKED в полёте публикует MISSION_ABORT/RETURN_HOME

Так вы демонстрируете: изоляцию + принудительное посредничество + минимальный доверенный код.

## Рекомендации с учётом использования Kafka в ЦД и Mosquitto с физическими дронами

Хорошо — тогда стоит сразу спроектировать “ядро” так, чтобы смена транспорта Kafka -> Mosquitto(MQTT) на 2‑м этапе была заменой адаптера, а не переписыванием бизнес-логики и тестов.

Ниже — практичные рекомендации, как это сделать.

▎1) Архитектурный принцип: транспорт — сменный, контракты — неизменны

Чтобы переход прошёл гладко, зафиксируйте на этапе симуляции:

1) Единый формат сообщений (envelope + schema + type + msg_id + ts).
2) Единые “логические каналы” (топики/темы), которые потом 1:1 маппятся на MQTT-топики.
3) Слой абстракции над брокером в коде (интерфейс шины).

Минимальный интерфейс (идея):
• publish(topic, message, headers)
• subscribe(topic, handler, group_id)
• request_reply(...) (если нужно) — лучше избегать, но иногда удобно в симуляции.

Это можно оформить как класс MessageBus + реализации KafkaBus и MqttBus.

▎2) Этап 1 (симуляция на Kafka): как разложить, чтобы потом не было больно

▎2.1. Топики Kafka делайте “MQTT-совместимыми”

Рекомендация: используйте имена топиков Kafka в стиле MQTT (с /), чтобы затем почти без изменений переехать:

• v1/D1_FLIGHT/cmd/mission.start
• v1/D1_FLIGHT/evt/telemetry
• v1/D3_EXTERNAL/evt/permit.issued
• v1/D2_OPS/evt/reg.status
• v1/D0_MEDIATION/audit/gateway

Kafka позволяет / в имени топика, и это сильно упрощает миграцию.

▎2.2. Семантики Kafka, которые стоит заложить сразу

• Партиционирование: ключом делайте uas_id или mission_id, чтобы сохранять порядок событий в рамках дрона/миссии.
• Идемпотентность: в каждом сообщении msg_id, а потребители держат дедупликацию (replay-cache).
• Контракты: JSON + schema версии; лучше сразу ввести JSON Schema в репозитории (даже без Confluent Schema Registry).

Структуры схем храните как файлы, например:
• schemas/v1/permit_issued.schema.json
• schemas/v1/reg_status.schema.json
• schemas/v1/mission_start.schema.json

▎2.3. Междоменная медиация остаётся центральной

Компонент interdomain-gateway в Kafka-мире делает то же, что и будет делать в MQTT-мире:
• принимает из “внешних/низкодоверенных” каналов,
• валидирует,
• применяет правила,
• публикует в “внутренние” каналы,
• пишет аудит.

Это как раз то, что хорошо “ложится” на конструктивную ИБ и почти не зависит от транспорта.

▎3) Этап 2 (физические дроны + Mosquitto): что поменяется по сути

▎3.1. MQTT — это “edge transport”, а Kafka — “backend log”

На практике часто получается гибрид:
• Дрон ↔ Mosquitto (MQTT, TLS, нестабильная связь, LWT, keepalive)
• Внутренние сервисы (аналитика/аудит/история) могут остаться на Kafka
• Между ними появляется мост mqtt-kafka-adapter (или два направления) — это и есть сменный слой транспорта

Даже если вы “переедете на Mosquitto целиком”, архитектурно полезно мыслить так: MQTT ближе к устройствам, Kafka ближе к хранению истории и интеграциям.

▎3.2. MQTT-специфичное, что надо учесть заранее (в контрактах и тестах)

MQTT даёт другие свойства, и тесты на 2‑м этапе должны это отражать:

• QoS: команды обычно QoS 1, телеметрия часто QoS 0/1 (зависит от ценности).
• Retained: для “текущего состояния” (например, reg.status.current) retained удобно, но осторожно — чтобы не “оживлять” устаревшее.
• LWT (Last Will): полезно для статуса “дрон оффлайн”.
• Сессии/переподключения: возможны повторы доставок → дедупликация по msg_id должна уже быть в ядре.
• Ограничения по размеру/частоте: телеметрия может потребовать агрегирования/батчинга.

▎3.3. Безопасность в Mosquitto (минимум для демонстрации)

На 2‑м этапе проще всего показать ИБ так:
• TLS + клиентские сертификаты (mTLS) для дронов
• ACL по топикам (каждый дрон может писать только в свои .../evt/... и читать только свои .../cmd/...)
• interdomain-gateway/policy — отдельная учётка с ограниченным “сквозным” доступом

▎4) План миграции, чтобы не ломать код и отчёт

1) Уже сейчас (Kafka) зафиксировать:
   • имена “логических топиков” в MQTT-стиле,
   • envelope сообщений + набор схем,
• правила interdomain-gateway и ops-policy-enforcer.

2) В коде всех сервисов использовать только интерфейс MessageBus, а не Kafka-клиент напрямую.

3) На 2‑м этапе добавить реализацию MqttBus и (опционально) сервис mqtt-kafka-adapter:
   • вариант A: “перенос полностью на MQTT” — отключаете KafkaBus
   • вариант B: “MQTT на краю, Kafka внутри” — оставляете KafkaBus для ядра, добавляете адаптер

4) Тесты:
   • E2E сценарии (AGR/INSP/CARGO) оставить идентичными по логике,
   • добавить слой “транспортных” тестов: KAFKA-... на этапе 1 и MQTT-... на этапе 2 (QoS, reconnect, LWT, ACL).

▎5) Уточнения, чтобы я дал конкретику (конфиги/ACL/топики)

Ответьте, пожалуйста, на 3 вопроса — и я предложу точную схему топиков + ACL + набор тестов под Kafka сейчас и под Mosquitto потом:

1) На этапе 2 вы хотите “только Mosquitto” или “Mosquitto для дронов + Kafka для внутреннего ядра”?
2) Сколько предполагается физических дронов (1–3 или больше) и будет ли у каждого свой uas_id?
3) Нужны ли команды “почти real-time” (например, ручное управление), или только миссии/waypoints и телеметрия?   

### Рекомендации с учётом второго этапа (интеграция с физическими дронами и срочными командами)

Понял: этап 2 — только Mosquitto, 20–40 БВС, от ОрВД нужны “почти real‑time” команды (pause, abort, обновление БПЗ/NFZ). Тогда лучше сразу стандартизировать MQTT-иерархию, QoS/retained, ACK‑паттерн и ACL так, чтобы:

• команды доходили предсказуемо (и было подтверждение исполнения),
• широковещательные обновления (NFZ) не «протекали» между дронами лишним,
• безопасность (mTLS + ACL) была демонстрируемой и проверяемой.

Ниже — рекомендуемая схема.

▎1) Иерархия MQTT-топиков (v1)

Разделите на: пер-дроновые команды/события + глобальные рассылки + сервисные статусы.

Пер-дроновые (строгая изоляция):
• v1/uas/<uas_id>/cmd/pause — приостановка
• v1/uas/<uas_id>/cmd/abort — прерывание (RTB/land/kill-switch — как договоритесь)
• v1/uas/<uas_id>/cmd/nfz.patch — частные для борта изменения (если нужно адресно)
• v1/uas/<uas_id>/evt/telemetry
• v1/uas/<uas_id>/evt/position
• v1/uas/<uas_id>/evt/cmd.ack — подтверждения команд
• v1/uas/<uas_id>/evt/alert — аварии/геозона нарушена/RTB начат

Глобальные (одна публикация — много получателей):
• v1/global/cmd/nfz.update — обновление бесполётных зон (для всех)
• v1/global/evt/system — объявления/режимы, если надо

Статусы подключения (LWT, retained):
• v1/uas/<uas_id>/status/conn — online/offline, timestamp, причина

Почему так: команды “почти real‑time” (pause/abort) лучше держать только per-uas, а NFZ — глобально, чтобы не делать 40 одинаковых publish.

▎2) Формат сообщений (envelope) — обязателен для дедупликации и аудита

Для команд и ACK:

{
  "schema": "uas.cmd.pause.v1",
  "msg_id": "01HZY...ULID",
  "ts": "2026-03-06T12:34:56.789Z",
  "issuer": "orvd.D2",
  "uas_id": "UAS-0021",
  "ttl_ms": 2000,
  "payload": {
    "mode": "HOLD_POSITION",
    "reason": "traffic_conflict"
  }
}


ACK (дрон → ОрВД/ядро):

{
  "schema": "uas.evt.cmd_ack.v1",
  "msg_id": "01HZY...ULID",
  "ts": "2026-03-06T12:34:56.950Z",
  "uas_id": "UAS-0021",
  "payload": {
    "ref_msg_id": "01HZY...ULID",
    "cmd": "pause",
    "status": "ACCEPTED", 
    "detail": "Entering loiter"
  }
}


Ключевое:
• msg_id + дедупликация на борту (и на стороне потребителей).
• ttl_ms (см. MQTT v5 ниже) — чтобы “pause через 30 секунд” не прилетал как актуальный.

▎3) QoS / retained / MQTT v5 — профили по типам сообщений

Команды “почти real-time”:
• QoS 1 (баланс: доставка “хотя бы раз” + приемлемая задержка).
• не retained.
• MQTT v5: Message Expiry Interval = 1–3 секунды (или из ttl_ms), чтобы брокер выкинул просроченное.

ACK:
• QoS 1, не retained.

NFZ update (глобально):
• обычно QoS 1.
• часто удобно retained (новый дрон/переподключившийся сразу получит актуальную NFZ).
• обязательно в payload: version, valid_from, hash (чтобы борт мог понять “это новое/то же самое”).

Телеметрия:
• QoS 0 (если высокая частота) или QoS 1 (если редкая и важная).
• не retained.

Статус conn (LWT):
• retained = true (последнее состояние “online/offline” всегда видно).
• LWT публикует offline при разрыве; при подключении борт публикует online.

▎4) Команды pause/abort: обязательно 2‑фазная трактовка

Для демонстрации управляемости и ИБ лучше формализовать:

1) ОрВД публикует команду в v1/uas/<id>/cmd/<...> (QoS1, expiry 2s).
2) Борт отвечает в v1/uas/<id>/evt/cmd.ack:
   • ACCEPTED (принял к исполнению) и затем отдельным событием evt/mission.state или вторым ACK COMPLETED.
   • либо REJECTED (например, “не могу удерживать позицию — ветер/батарея”).
3) ОрВД/мониторинг ставит таймаут: если нет ACCEPTED за T (например, 500–800 ms в лабораторных условиях / 1–2s в полевых), поднимает тревогу.

Важно: MQTT не гарантирует “строго real-time”, поэтому на борту всё равно нужен fail-safe: если канал управления пропал, дрон сам уходит в заранее согласованный режим (loiter/RTB/land) — это отдельная политика безопасности.

▎5) ACL и mTLS в Mosquitto (20–40 БВС)
Лучший практический минимум: mTLS + ACL, где каждый борт видит только своё.

▎5.1. Идентичность

Сертификат на борт с CN вида UAS-0021 (или SAN). В Mosquitto можно использовать CN как username.

▎5.2. Пример acl_file с pattern (Mosquitto 2.x)

Файл mosquitto.acl:

# Каждый клиент (по CN) имеет доступ только к своему дереву
pattern read  v1/uas/%c/cmd/#
pattern write v1/uas/%c/evt/#
pattern readwrite v1/uas/%c/status/#

# Всем дронам разрешить читать глобальные NFZ
topic read v1/global/cmd/nfz.update

# ОрВД (отдельный клиент) может публиковать команды всем и читать события
user orvd
topic write v1/uas/+/cmd/#
topic read  v1/uas/+/evt/#
topic read  v1/uas/+/status/#

# Сервис мониторинга (пример)
user ops
topic read v1/uas/+/evt/#
topic read v1/uas/+/status/#
topic read v1/global/#


Это даёт понятную демонстрацию “междоменного контроля”: борт не может публиковать в чужие топики, ОрВД — может командовать, OPS — наблюдать.

▎6) Настройки Mosquitto, которые прямо влияют на “почти real-time”

Минимально полезные моменты:
• per_listener_settings true, отдельный listener под mTLS.
• Ограничить очереди, чтобы команды не “копились”:
  – max_queued_messages (в разумных пределах)
  – MQTT v5 expiry (предпочтительно, чем глобальные лимиты)
• persistent_client_expiration — чтобы не держать мусорные сессии вечно.
• Keepalive у дронов, например 5–15 секунд (в зависимости от канала).

Если канал нестабилен: делайте сессии persistent (не clean start), но *команды* всё равно должны иметь expiry, иначе при восстановлении связи дрон получит устаревшее abort.

▎7) NFZ update: как передавать (чтобы не убить MQTT payload)

Если NFZ может быть большой:
• вариант А (часто лучший): в v1/global/cmd/nfz.update передавать метаданные + URL (или object storage key) и хэш, а борт скачивает по HTTPS.
• вариант Б: передавать GeoJSON целиком, но следить за размером (и частотой).

В любом случае: version монотонно растущая + hash, чтобы борт не применял “старое”.
