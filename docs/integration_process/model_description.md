# Model description: interaction scenarios v2.0

Документ описывает **модель (архитектуру) взаимодействия** ключевых систем в контрактном API v2.0.
Формат намеренно **сценарный/архитектурный** (без полного покомпонентного списка полей), чтобы:
- закрыть ключевые пропуски в текущем `change_requests.md`,
- сделать явными точки, где применяется `security_goals`,
- заложить расширяемость под другие сценарии (доставка, инспектирование) без изменения envelope.

## 1) Базовые принципы контракта v2.0

1. Все межсистемные взаимодействия идут через брокеры (Kafka/Mosquitto) и **центральный журнал**, который также принимает сообщения через брокер.
   Центральный журнал записывает:
   - все внешние события (между системами),
   - а также внутренние события, которые собираются внутренними журналами систем.
2. Envelope использует маршрутизацию по `action`.
3. request/response строится вокруг механики transport/SystemBus (`correlation_id` + `reply_to`).
4. Центральный журнал переиспользует текущий контракт EventJournal (в документации — `emit_event`, severity и т.д.).

## 2) Модель `security_goals` (ключевое требование Запроса 6)

### 2.1 Источник целей

- Для каждой системы определяется набор `system_security_goals`.
- Для каждого заказа определяется набор `order_security_goals`.
- Полные описания целей стандартизированы и доступны у Регулятора; **в сообщениях передаются только ID** (`List[str]`).

### 2.2 Производство `order_security_goals`

В постановке для v2.0 принято:
- `order_security_goals` **формирует агрегатор** на основании параметров заказа и шаблонов v2.0.
- отдельный runtime-запрос к Регулятору на каждом шаге не обязателен (если не требуется в будущем).

Правило для пустого списка:
- при `order_security_goals = []` выбор контрагента/исполнителя делается на основе автоматически определённого Агреатором минимального набора целей безопасности для конкретной задачи;
- если и Агреатор не выявил необходимые цели безопасности, то допускаются любые БАС, а окончательный выбор осуществляется Заказчиком на основе стоимости.

### 2.3 Две обязательные точки фильтрации контрагентов

1) Фильтрация на стороне Агрегатора  
- применяется при формировании предложения/выборе контрагента.
- если контрагент не покрывает `order_security_goals`, контрагент **отбраковывается**.

2) Фильтрация на стороне ОрВД БАС (в контуре approval/validate миссии)  
- применяется при проверке миссии и пригодности исполнителя/БАС к миссии.
- при несоответствии оркестратор/ОрВД фиксирует отказ и требует остановить/не допустить миссию.

### 2.4 Модель отклонения (rejection)

Для унификации важно фиксировать:
- в случае отказа должен быть возвращаемый результат, в котором присутствует:
  - какие goal_id стали причиной (`rejected_by_security_goals`)
  - тип причины/код (`reason_code`)
  - опциональные детали (candidate, mission_id, violated constraints).

## 3) Сценарная модель взаимодействия (coverage пар из Запроса 6)

Ниже перечислены сценарии как **модель стадий**, а не конкретные схемы полей.
Для каждого сценария указано:
- роль отправителя/получателя,
- где применяется `security_goals`,
- как должен выглядеть результат (успех/отбраковка).

### 3.1 Customer → Aggregator (receive_order)

Цель: Customer инициирует выполнение задачи, агрегатор принимает заказ в работу.

Вход:
- параметры заказа (включая цели/покрытие, сценарий типа доставки/инспекции и т.п.).

security_goals:
- сценарные цели безопасности (цб) указываются Заказчиком явно в запросе;
- Агрегатор по типу и координатам запроса определяет набор цб и формирует `order_security_goals`;
- `order_security_goals` может быть явно приложен к сообщению агрегатора дальше (например, в предложениях/ответах), чтобы получатели могли объяснить отказ.

Результат:
- accept/reject по валидности заказа.
- при успехе агрегатор переводит заказ в состояние “received”.

### 3.2 Aggregator → Operator (receive_order → proposal)

Цель: агрегатор запрашивает у Эксплуатанта предложение под заказ.

security_goals:
- перед отправкой в Operator агрегатор обязан отфильтровать контрагентов по покрытию `order_security_goals`.
- в response от Operator агрегатор (и дальше Customer) должен получить объяснимые результаты (в том числе фактические `applied_security_goals` или минимум — набор, на основе которого предложение было сформировано).

Результат:
- успех: формируется `proposal` (id/price/margin/время/привязка к order и применённым goal_id).
- отказ: возвращается `error` и/или `rejection` с `rejected_by_security_goals`.

### 3.3 Operator → Insurer (request_insurance_quote)

Цель: запрос страховой оценки/котировки под миссию/покрытие.

security_goals:
- страховой расчет должен учитывать требования, которые зависят от целей безопасности заказа (минимально — обязательная “обвязка” полиса/котировки целями).

Результат:
- success: quote_id + premium + coverage + valid_until.
- отказ: либо error, либо denial (в будущем можно унифицировать через rejection).

### 3.4 Operator → Developers (purchase_uas / find_available_uas)

Цель: выбор и покупка подходящих БАС.

security_goals:
- при выборе БАС учитываются цели безопасности (в части сертификации/допустимости операций).
- при покупке/подборе важно фиксировать, какие goal_id “покрыты” конкретной БАС-моделью/сертификацией.

Результат:
- success: purchased UAS (или suitable list) + успех/статусы.
- denial: `error` и/или `rejection` с причинами (goal_id).

### 3.5 Operator ↔ DronePortGCS

Цель: получение/передача данных для запуска/сервиса миссии на стороне наземной инфраструктуры.

security_goals:
- DronePortGCS должен иметь возможность запретить старт/операции, если миссия/исполнитель не удовлетворяют security требованиям.

Результат:
- конфигурация миссии для DronePortGCS.
- в дальнейшем: расширение под мобильные дронопорты и расписания зарядки (scenario.details).

### 3.6 Operator ↔ NUS (mission planning / регистрации миссии)

Цель: НУС формирует детали миссии под конкретного исполнителя/БАС.

security_goals:
- НУС и/или Operator должен сохранить `order_security_goals` и передать их в контур ОрВД на этапе validate/approval.

Результат:
- `mission_details` (draft/статус) + идентификаторы.
- при отклонении: failure/denial (пока без унифицированного rejection, но контракт должен быть расширяемым).

### 3.7 NUS → Agro-drone (agro mission planning)

Цель: построить план опрыскивания/агро-задачи и выделить подходящий БАС.

security_goals:
- применяются цели безопасности, привязанные к сценарию (agro) и к исполнительному БАС.

Результат:
- selected_uas + agro_mission_plan.

### 3.8 Agro-drone ↔ SITL

Цель: симуляция поведения/движения, имитация помех и телеметрии.

security_goals:
- в этом контуре достаточно фиксировать сценарий и привязку к миссии; security фильтрация должна происходить раньше (в контуре ОрВД/authorize).

Результат:
- simulation_result + отчет/телеметрия (на уровне структуры).

### 3.9 Operator ↔ UTM/OrВД БАС (approval / validate mission)

Цель: разрешить миссию в воздушном пространстве.

security_goals (обязательная 2-я точка фильтрации):
- ОрВД получает `mission_security_goals` (обычно order_security_goals + сценарные добавки).
- если несоответствие — ОрВД отклоняет миссию, возвращает отказ и требует остановить исполнение.

Результат:
- approved=true/false.
- при denial: `rejection` с `rejected_by_security_goals` и reason_code.

### 3.10 Всеми системами → Regulator (get_system_topics / get_security_goals / get_regulations / report_incident)

Цель: получить справочные сведения и/или отправить события инцидентов.

security_goals:
- для унификации contract v2.0 предполагается действие уровня “справочник целей”:
  - где-то в контуре v2.0 должен существовать контракт `get_security_goals` (по system/component).

Результат:
- возвращается `security_goals` (возможно с описаниями, но в рабочих payload’ах используются только goal_id).

## 4) Критические пропуски в текущем описании (перед реализацией v2.0)

Эти моменты стоит закрыть в будущих версиях описания/контракта (или в следующем проходе v2.0):

1. Не определена единая форма `rejection` для всех “security-based” отказов  
- где, например, агрегатор и ОрВД должны возвращать `rejected_by_security_goals` и `reason_code` в одинаковом стиле.

2. Не зафиксирована явная привязка `order_security_goals` к “покрытию контрагентами”  
- т.е. какое именно правило покрытия используется (coverage_mode) и как трактовать пустой список.

3. Не описано, какие именно события центральный журнал должен фиксировать  
- особенно для этапов:
  - “агрегатор отбраковал контрагентов из-за security_goals”,
  - “ОрВД отклонил миссию из-за security_goals”,
  - “успех: какие goal_id реально применились”.

4. Расширяемость под delivery/inspection задана только концептуально  
- требуется договориться, как именно добавляются сценарные goal’ы:
  - на уровне `order_security_goals` (base + addon),
  - или на уровне `scenario.details` с дальнейшим выводом.

## 5) Открытые вопросы (нужны для финализации контрактного v2.0 в notebook)

1. `coverage_mode` для `security_goals`
   - в v2.0 фиксируется поведение для пустого списка: см. правило в разделе `2.2 Производство order_security_goals`.

2. Центр. журнал: минимальный каталог `event_type` для security_goals
   - так как центральный журнал записывает и внешние события, и внутренние события из журналов систем, для финализации v2.0 нужно зафиксировать:
     - какие `event_type` используются для отображения фильтрации контрагентов по `security_goals` на стороне Агрегатора,
     - какие `event_type` используются для отображения отказа/отбраковки миссии из-за `security_goals` на стороне ОрВД БАС,
     - какие `event_type` используются для фиксации применённых goal_id (успех) и причины (rejection).

## Дополнения к сценарию взаимодействия

Агрегатор работает со многими Эксплуатантами, Агрегатор рассылает по Эксплуатантам запрос на предложение для запроса Заказчика. 

Эксплуатанты выбирают из своих БАС подходящие по запросу (для этого проверяет через Дронопорты местоположение и доступность БАС для задачи), для этих БАС запрашивают стоимость страховки, отправляют итоговое предложение Агрегатору. 

Агрегатор передаёт подходящие по целям безопасности, максимальной стоимости и иным параметрам предложения Заказчику. Заказчик выбирает исполнителя заказа по полученным предложениям. 

Выбранный исполнителем Эксплуатант получает от Агрегатора заказ, через НУС рассчитывает миссию, согласовывает с ОрВД БАС. 

Если ОрВД БАС миссию согласовывает, Эксплуатант оплачивает страховку на миссию и через связку НУС и Дронопорт отправляет БАС в полёт. 

Перед вылетом БАС запрашивает разрешение на вылет, ОрВД БАС проверяет, что параметры миссии была ранее согласованы, есть оплаченная страховка.  

Разрешение на вылет передаётся Дронопорту, чтобы он "физически" допустил вылет конкретной БАС. После этого разрешает вылет БАС. 

БАС проверяет допуск к вылету со стороны Дронопорта. Только после этого БАС вылетает по маршруту.
