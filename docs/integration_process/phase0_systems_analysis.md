# Анализ реализаций в `systems/` и отклонения от ТЗ (этап 0)

**Дата:** 2026-03-19  
**Основание:** [integration_tasks.md](integration_tasks.md), задача 1; ТЗ — [requirements_spec.md](../requirements_spec.md).  
**Ограничение:** документ фиксирует состояние на момент анализа; изменения кода не выполнялись.

---

## 1. Цель этапа 0 (из формулировки задачи)

Должно обеспечиваться:

1. Взаимодействие **Заказчика** с **Агрегатором**.
2. **Агрегатора** с **Эксплуатантом**.
3. **Эксплуатанта** со **Страховой компанией**, **НУС**, **Дронопортом**, **ОрВД БВС**.
4. Возможность **заказать услугу обработки полей агро-дроном**.

## 3. Соответствие цепочке этапа 0

### 3.1. Заказчик → Агрегатор

**Реализовано:** REST API Агрегатора для регистрации заказчика и создания заказа. Заказчик как отдельное приложение в репозитории не выделен — предполагается клиент (curl, Postman, скрипт).

**Замечание:** для «обработки полей» текущая модель заказа в README Агрегатора ориентирована на **доставку** (маршрут `from_*` / `to_*`, бюджет), не на полигон агро-работ.

### 3.2. Агрегатор → Эксплуатант

**Реализовано частично:** Агрегатор публикует в Kafka сообщения `create_order`, `confirm_price` и читает `price_offer`, `order_result`. Эксплуатант обрабатывает заказы через брокер и компонент `operator_system` (логика `_handle_receive_order` и др.).

**Разрыв:** Агрегатор в [change_requests.md](../../systems/operator/docs/change_requests.md) явно указан как работающий **только с Kafka**; Эксплуатант по умолчанию использует **MQTT**. Для сквозной интеграции нужна согласованная конфигурация (Kafka + общие топики/префиксы) или задокументированные заглушки для MQTT.

**Разрыв по именованию:** префиксы топиков Агрегатора (`v1.aggregator_insurer.<instance>.…`) и абстракция Эксплуатанта (`systems.aggregator.<id>` в `topics.py`) **не совпадают** без явного слоя сопоставления или общей спецификации.

### 3.3. Эксплуатант → Страховая

**Реализовано частично:** в Эксплуатанте заданы идентификаторы и темы для страховой; в Страховой — свой формат Kafka и JSON (`requestType`, …).

**Разрыв:** нет в репозитории единого **контракта** (одинаковые имена топиков и тела сообщений), подтверждающего готовность сквозного сценария без доработки одной из сторон или адаптера.

### 3.4. Эксплуатант → НУС (DronePortGCS)

**Статус:** в [change_requests.md](../../systems/operator/docs/change_requests.md) (запрос 5) интеграция с НУС **запланирована**: передача подтверждённого задания, подготовка миссии для ОрВД. Реализация на стыке требует отдельной проверки совместимости топиков DronePortGCS и Эксплуатанта.

### 3.5. Эксплуатант → Дронопорт

**Статус:** в том же change request указано, что **реализация Дронопорта не готова**; для тестов предполагается заглушка или отложенный интерфейс.

### 3.6. Эксплуатант → ОрВД БВС

**Статус:** в коде Эксплуатанта присутствует привязка к «ОрВД» через `UTM_ID` и события миссий (`mission_validated` и др. в `event_types.md`). Полноценный контур ОрВД как отдельной системы в `systems/` **не выделен** как готовый сервис этапа 0 — ожидается заглушка или внешний симулятор.

### 3.7. Заказ услуги «обработка полей агро-дроном»

**Реализовано частично:** в Эксплуатанте есть события и логика, связанные с **агродроном** (например `agro_uas_selected`, см. `systems/operator/docs/event_types.md`). Система **agrodron** в `cyber_drons` документирует взаимодействие с НУС/ОРВД/Дронопортом.

**Разрыв:** Агрегатор не описывает тип услуги «агро-обработка полей» в том виде, в каком сформулирована цель этапа 0; связка «HTTP заказ → Kafka → Эксплуатант → агродрон» **не зафиксирована** как завершённый E2E в общей документации интеграции.

## 4. Отклонения от [requirements_spec.md](../requirements_spec.md)

Условные обозначения: **О** — отклонение, **Ч** — частичное соответствие.

### 4.1. Развёртывание (Р1–Р3, СП1)

| Требование | Оценка | Комментарий |
|------------|--------|-------------|
| Р1 Makefile / shell | Ч | В корне есть [Makefile](../../Makefile) с `init`, `tests-*`, `docker-up` для **брокера** ([docker/docker-compose.yml](../../docker/docker-compose.yml)). Нет целей `build-all`, `build-docker`, `run-all`, `run-all-docker`, `tests-all`, `tests-all-docker` в форме, описанной в РФ1. |
| Р2 docker-compose всех сервисов | Ч | Общий compose в `docker/` поднимает Kafka/Mosquitto; **не** все прикладные системы. У Агрегатора, Оператора, Insurer и др. — **отдельные** compose-файлы. |
| Р3 разработка в контейнере | Ч | Частично покрыто README/Makefile отдельных систем; единого сценария в корне нет. |
| СП1 `make build-docker` в корне | О | В корневом Makefile цель `build-docker` отсутствует. |

### 4.2. Структура репозитория (РФ1)

| Требование | Оценка | Комментарий |
|------------|--------|-------------|
| `broker/` в корне | О | Брокер описан через `docker/docker-compose.yml`, отдельной папки `broker/` как в шаблоне нет. |
| Единый `docker-compose.yaml` в корне | О | Используется `docker/docker-compose.yml`, не имя/путь из шаблона РФ1. |
| Системы в `systems/systemX` с подкаталогом `componentY` | Ч | Фактически `systems/operator/src/<component>/` и т.п.; соответствие шаблону не дословное. |

### 4.3. Архитектура (А2)

| Требование | Оценка | Комментарий |
|------------|--------|-------------|
| Взаимодиествие через брокер | Ч | Агрегатор ↔ клиент по HTTP (допустимо как внешний интерфейс). Между Агрегатором и Эксплуатантом — брокер, но **два разных продукта** (Kafka vs MQTT по умолчанию) усложняют соблюдение единого правила без договорённости. |

### 4.4. Документация (Д3)

| Требование | Оценка | Комментарий |
|------------|--------|-------------|
| PlantUML последовательности, `docs/diagrams` сервиса | Ч | У Эксплуатанта есть диаграммы; **сквозная** диаграмма «этап 0» на уровне всего продукта в `docs/integration_process/` не обязательна по ТЗ сервиса, но для интеграции желательна. |
| Таблицы интерфейсов | Ч | Разрозненно по README систем. |

### 4.5. Тесты (КК*, папки tests)

| Требование | Оценка | Комментарий |
|------------|--------|-------------|
| КК5 `make tests-all` | О | В корне — `make tests`, не `tests-all`. |
| КК3 e2e/integration пути | Ч | Есть `tests/` в корне; дублирование нумерации **КК3** в ТЗ — дефект текста спецификации. |

### 4.6. Базовые требования к системам (БТ*)

Для этапа 0 релевантны в первую очередь: брокер между доменами (БТ2), журналирование (БТ13), телеметрия/события в аналитику (БТ10–БТ11), сертификаты (БТ12) — **полное соответствие** по репозиторию на момент анализа **не подтверждено** без отдельного аудита каждой системы.

## 5. Внешние источники требований внутри репозитория

Файл [systems/operator/docs/change_requests.md](../../systems/operator/docs/change_requests.md) содержит **детальный бэклог** по интеграции Агрегатор ↔ Эксплуатант ↔ Страховая ↔ НУС ↔ Агродрон, общему Makefile, тестам и демо. Он **согласуется** с выявленными разрывами и должен учитываться при планировании этапа 0.

## 6. Выводы

1. **Цепочка этапа 0** в репозитории представлена **набором частично совместимых** систем; готового «одного compose — полный сценарий агро-заказа» в описании интеграции **нет**.
2. Главные технические риски: **единый транспорт и топики** Агрегатор ↔ Эксплуатант; **выравнивание Kafka** со Страховой; **НУС/агродрон**; **заглушки** Дронопорта и ОрВД.
3. **ТЗ по развёртыванию и корневому Makefile** фактически **не выполнено** в части целей РФ1/СП1 — это отклонение следует либо закрывать работами, либо формализовать как допустимое для учебного прототипа (решение владельца продукта).

См. перечень замечаний и технических задач: [phase0_remarks_and_technical_tasks.md](phase0_remarks_and_technical_tasks.md).
