## Часть A. Замечания

| ID | Область | Суть замечания |
|----|---------|----------------|
| З1 | Интеграция Агрегатор ↔ Эксплуатант | Агрегатор использует **Kafka**; Эксплуатант по умолчанию **MQTT**. Без единой конфигурации и общих топиков сквозной сценарий не воспроизводим. |
| З2 | Имена топиков | Префиксы/паттерны топиков Агрегатора (`v1.aggregator_insurer…`) и Эксплуатанта (`systems.aggregator…` и др.) **не совпадают**; отсутствует опубликованная **topic map** для этапа 0. |
| З3 | Страховая | Схема Kafka в `systems/insurer` (`v1.Insurer.*.insurer-service.*`) **отличается** от соглашений Агрегатора/Эксплуатанта; сквозной обмен не подтверждён документом контракта. |
| З4 | Предметная область | Цель этапа 0 — заказ **обработки полей агро-дроном**; API Агрегатора описан под **доставку** (геомаршрут). Нет согласованной модели заказа «агро». |
| З5 | НУС | Интеграция Эксплуатанта с `systems/DronePortGCS` **в процессе** (см. change_requests); совместимость топиков и сценариев требует проверки. |
| З6 | Дронопорт | Явно зафиксировано отсутствие готовой реализации Дронопорта; для тестов нужны **заглушки** или отложенный интерфейс. |
| З7 | ОрВД БВС | Отдельной готовой системы ОрВД в `systems/` нет; используются идентификаторы/события (**UTM**), возможны только заглушки/симулятор на этапе 0. |
| З8 | ТЗ: корневой Makefile | В [requirements_spec.md](../requirements_spec.md) (РФ1) перечислены цели `setup`, `build-all`, `build-docker`, `run-all`, `run-all-docker`, `tests-all`, `tests-all-docker`. В корневом [Makefile](../../Makefile) они **не реализованы** в полном объёме. |
| З9 | ТЗ: docker-compose | Ожидается единый запуск всех сервисов; фактически — **инфраструктура брокера** в `docker/` + **разрозненные** compose в подсистемах. |
| З10 | ТЗ: структура `broker/` | В шаблоне РФ1 указана папка `broker/` в корне; в текущей компоновке брокер **встроен** в `docker/docker-compose.yml`. |
| З11 | Документация ТЗ | В [requirements_spec.md](../requirements_spec.md) дважды пронумеровано **КК3** (разные формулировки) — стоит исправить редакцию ТЗ. |
| З12 | Согласованность с change_requests | Крупный объём требований к интеграции уже изложен в [systems/operator/docs/change_requests.md](../../systems/operator/docs/change_requests.md); риск **дублирования** и расхождения приоритетов с этапом 0. |

## Часть B. Технические задачи (бэклог)

Приоритет: **P0** — блокер для минимального этапа 0, **P1** — важно для воспроизводимости, **P2** — выравнивание с ТЗ и качеством.

### B.1. Контракты и интеграция

| ID | Приоритет | Задача |
|----|-----------|--------|
| Т1 | P0 | Утвердить и задокументировать **единый транспорт** для пары Агрегатор ↔ Эксплуатант на этапе 0 (**Kafka** + общий кластер/сеть, см. change_requests). |
| Т2 | P0 | Составить **таблицу топиков** (producer, consumer, формат JSON, версия протокола) для Агрегатора, Эксплуатанта, при необходимости — Страховой и НУС. |
| Т3 | P0 | Расширить или заменить модель заказа Агрегатора полями **типа услуги** (например `service_type: delivery | agro_field`) и минимальным набором полей для **агро** (полигон, культура, окно времени — по согласованию с продуктом). |
| Т4 | P1 | Реализовать или описать **адаптер** сообщений Страховой ↔ Эксплуатант (выравнивание имён топиков и payload). |
| Т5 | P1 | Провести **стыковку топиков** Эксплуатант ↔ DronePortGCS (НУС): список сообщений «задание подтверждено → миссия → регистрация ОрВД». |
| Т6 | P1 | Ввести **заглушку Дронопорта** (контракт из `cyber_drons` docs) для автотестов без реальной реализации. |
| Т7 | P1 | Ввести **заглушку ОрВД** (ответы на запросы миссии/валидции) или задокументировать использование существующего mock в Mission Planner. |
| Т8 | P2 | Связать сценарий агро-заказа с **systems/cyber_drons/agrodron** (тестовые данные, E2E согласно change_requests). |
